## 一、核心概念

### 什么是 Hermes Agent
由 Nous Research 于 2026 年 2 月发布的开源 AI Agent 框架。它被定义为**「第一个出厂就带缰绳的 AI Agent」**，是 Harness Engineering 方法论的首次产品化。

### Nous Research 的设计取向

- 开源 AI 研究实验室，核心人物 Teknium 主导
- Hermes 模型家族从 8B 到 405B，纯靠后训练达到前沿水平
- 核心原则：**用户控制优先**、模型可控（steerable）、不做内容审查
- 理念：**不是替你做决定，而是你设规则、它学规则、然后越做越好**

### Harness 五组件的内建化

| Harness 组件 | 手动实现方式 | Hermes 内建系统 |
|---|---|---|
| 指令层 | 手写 CLAUDE.md | Skill 系统（自动创建+自改进） |
| 约束层 | 配置 hooks / linter | Tool permissions + sandbox |
| 反馈层 | 人工审查 | 自改进学习循环 |
| 记忆层 | 手动维护 knowledge base | 三层记忆 + Honcho 用户建模 |
| 编排层 | 自己搭多 Agent pipeline | 子 Agent 委派 + cron 调度 |

## 二、Hermes Agent 全景（60 秒看懂）

### 架构一张图

整个 Hermes 可以用一条流水线串起来：

```
学习循环 → 三层记忆 → Skill系统 → 40+工具 → 多平台Gateway
```

每个模块的职责：

- **学习循环（心脏）**：每次任务后自动复盘——该记什么、该提炼什么 Skill、Skill 要不要优化
- **三层记忆（大脑）**：会话记忆 + 持久记忆 + Skill 记忆，SQLite + FTS5 按需检索
- **Skill 系统（技能库）**：markdown 文件存于 `~/.hermes/skills/`，三种来源（自带/自创/Hub），**使用中自我改进**
- **40+ 内置工具（手脚）**：执行/信息/媒体/记忆/协调五大类，加 MCP 接入 6000+ 应用
- **多平台 Gateway（入口）**：Telegram、Discord、Slack 等 12+ 平台

>**一句话区分OpenClaw与Hermes：** OpenClaw 是你养出来的龙虾（靠你用心喂养），Hermes 是自己会长大的龙虾（靠自己从经验中学习）。

## 三、核心机制

### 1. 学习循环：Agent 自己给自己造缰绳（§03）

学习循环是 Hermes 的心脏，由**五个环节串成一个正反馈飞轮**：

```
策划记忆 → 创建 Skill → Skill 自改进 → FTS5 召回 → 用户建模
```

**环节一：策划记忆（主动决定记什么）**

不是被动存储所有对话，而是每轮结束后**主动判断**：这次聊了什么？有新发现吗？用户表达了什么偏好？值得记的写入 SQLite，建 FTS5 索引。还有周期性 nudge 机制定时提醒回顾。

**环节二：自主创建 Skill**

完成复杂任务后，Hermes 会问自己：这个解决方案以后还会用到吗？如果是，就提炼成 `~/.hermes/skills/` 下的 markdown 文件。例如做完一次 CSV 清洗入库后，可能自动生成 `csv-to-database.md`，下次直接复用。

**环节三：Skill 自改进**

Skill 不是写完就结束。每次使用时如果用户给了反馈（如"这个导入应该先检查表是否存在"），Hermes 不只是这次加上，**它会回头修改 Skill 文件本身**。下次默认就带上这个检查。

**环节四：FTS5 跨会话召回**

不是把历史全塞进上下文，而是按当前话题用 FTS5 全文检索相关片段。**纯本地存储**，搬家时拷贝 `~/.hermes/` 目录即可。

**环节五：用户建模（Honcho）**

可选外挂，比"记你说过什么"更进一步：**推理你是什么样的人**。从行为模式归纳特征，注入后续对话的隐形上下文。

> **核心洞察**：传统 AI 的记忆是对话记录的堆积，Hermes 的记忆是经验的蒸馏。一个是录像带，一个是笔记本——录像带越来越长终会溢出，笔记本可以一直用。

### 2. 三层记忆：从金鱼到老友（§04）

为什么记忆是最难的问题？活跃用户每天聊几千字，一个月几万字，全塞上下文要么装不下，要么模型注意力分散。**好的记忆不是存得多，是找得准。**

#### 第一层：会话记忆（情景记忆）

回答"**发生了什么？**"

- 所有对话内容、工具调用、返回结果全部写入 SQLite + FTS5 索引
- 关键设计：**按需检索而非全量加载**

| 方式 | 全量加载 | 按需检索（Hermes） |
|---|---|---|
| 上下文占用 | 随对话线性膨胀 | 基本恒定 |
| 检索精度 | 什么都在，什么都找不到 | 按关键词精准匹配 |
| 长期可用性 | 几天就撑不下 | 可用数月甚至数年 |
| 响应速度 | 越来越慢 | 基本不变 |

#### 第二层：持久记忆（语义记忆）

回答"**你是谁？**"

- 存的不是对话内容，是**从对话中提炼出的持久状态**：编码偏好、项目结构、工具链、工作时间规律
- 纯文件级方案，全部在 `~/.hermes/` 下
- **便携性极强**：备份到 U 盘、Docker 挂载、网盘同步都行

#### 第三层：Skill 记忆（程序性记忆）

回答"**怎么做事？**"

- 方法论和操作规范
- 每个 Skill 是可读可编辑的 markdown 文件

#### 三层协作的真实例子

用户说"帮我部署这个项目"：
1. **FTS5 搜会话记忆** → 找到上次部署的端口冲突问题
2. **查持久记忆** → 知道用阿里云 ECS、Nginx 反代
3. **加载 Skill** → `deployment-checklist` 按验证过的步骤执行

#### Honcho 辩证建模的厉害之处

它能捕捉**言行不一致**。比如你嘴上说"要写完整注释"，但实际 review 代码时从不看注释。Honcho 同时关注两者，从行为模式中归纳出真实偏好。

举例推断维度：
- 技术水平、工作节奏（晚上 9-11 点活跃）
- 沟通风格（喜欢先看结果再问原理）
- 目标推断（最近任务都围绕数据处理）
- 情绪模式（代码报错时简洁回答效果更好）
- 偏好矛盾（说一套做一套的地方）

#### 与 Claude Code 记忆系统的对比

| 维度 | Claude Code | Hermes Agent |
|---|---|---|
| 记忆格式 | CLAUDE.md + auto-memory 文本 | SQLite + FTS5 + Skill 文件 |
| 写入方式 | 手动写，半自动补充 | 全自动写入，人可覆盖 |
| 检索方式 | 启动时全量加载 | 按需 FTS5 检索 |
| 用户建模 | 无（要自己写偏好） | Honcho 自动推理 |
| 程序性记忆 | CLAUDE.md 中的指令 | 独立 Skill 文件，可自改进 |

> **重要提醒**：Hermes 目前**没有自动过期机制**，长期使用记忆会持续增长。也存在**记忆污染**风险——如果早期错误信息被记住，会持续影响后续行为。建议定期审查 `~/.hermes/skills/` 和持久记忆，删掉过时或错误的内容。

### 3. Skill 系统：会自我进化的能力（§05）

#### Skill 到底是什么

打个比方：教新同事做周报，第一次手把手带，第三次他自己搞定。**Skill 就是"第三次之后"的状态**，Agent 把方法固化成可复用文档。

三种来源：

| 来源 | 说明 | 数量级 |
|---|---|---|
| Bundled Skills | 安装时自带（MLOps、GitHub 工作流、研究等） | 40+ |
| Agent 自主创建 | 完成复杂任务后自动提炼 | 按使用积累 |
| Skills Hub | 社区一键安装 | 持续增长 |

#### agentskills.io：Skill 的通用语言

**这是被低估的设计**。已有 30+ 工具支持（Claude Code、Cursor、Copilot、Gemini CLI 等）。

- 给 Claude Code 写的 Skill 可直接在 Hermes 用
- 反过来也一样
- 不像 App Store 每个平台一套，更像 USB 接口——一个 Skill 插哪都能跑
- **Skill 是你自己的资产，不是某个平台的附属品**

#### 自改进机制（与所有其他 Agent 的最大区别）

四步闭环：

1. **执行 Skill**：按记录的步骤完成任务
2. **收集反馈**：用户反应（满意/不满意/修正）写入会话记忆
3. **更新 Skill**：Agent 分析反馈，自动修改 Skill 文件中的步骤
4. **下次使用新版本**：改进后的 Skill 在后续任务中自动生效

#### 实战例子:GitHub 日报 Skill 的诞生

前几次你都说："帮我看昨天的 GitHub 通知，按重要程度排序，PR 和 Issue 分开，忽略 bot。"

第三、四次后，Hermes 自动生成 `~/.hermes/skills/github-daily-digest.md`：

```markdown
# 触发条件
用户提到"GitHub 通知"、"每日总结"等关键词

# 执行步骤
1. 调用 GitHub MCP 获取过去 24 小时通知
2. 过滤 bot 账号
3. 按类型分组（PR / Issue / Discussion）
4. 按重要程度排序（mention > review request > 其他）

# 用户偏好
- 不需要详细内容，只要标题和状态
- PR 和 Issue 分开显示
```

之后你只说"看看 GitHub"，它就知道怎么做。某天你说"这次把 Discussion 也加上"——它**不只是这次加，会更新 Skill 文件本身**，下次默认带上。

#### Hermes Skill vs OpenClaw Skill

| 维度 | OpenClaw Skill | Hermes Skill |
|---|---|---|
| 创建方式 | 人工编写 SOUL.md | Agent 自创+人工编写 |
| 维护方式 | 人工更新 | 自动进化+人工干预 |
| 个性化 | 通用模板，用户 fork 自定义 | 从你的使用习惯自然生长 |
| 生态规模 | 44000+（大） | 40+ 预置+社区（成长中） |
| 互通性 | 都用 agentskills.io 标准 | 同 |

> **务实建议**：从 ClawHub 装 Skill 到 Hermes 里，然后让 Hermes 在使用中持续改进。两者不是替代关系。

> **Skill 自改进的前提**：你的反馈要够清晰。光说"不太对"但不说具体哪里不对，Agent 无法准确改进。**好反馈 = 好进化方向**。

### 4. 40+ 工具与 MCP:连接一切（§06）

#### 五大类工具速览

| 类别 | 核心工具 | 用途 |
|---|---|---|
| 执行类 | terminal、code_execution、file | 跑命令、执行代码（沙箱）、读写文件 |
| 信息类 | web、browser、session_search | 搜索、浏览器自动化、历史对话检索 |
| 媒体类 | vision、image_gen、tts | 理解图片、生图、文转语音 |
| 记忆类 | memory、skills、todo、cronjob | 操作记忆、管理 Skill、任务规划、定时 |
| 协调类 | delegation、moa、clarify | 委派子 Agent、多模型推理、请求澄清 |

**几个独特工具值得拎出来**：

- **session_search**：FTS5 全文索引搜历史对话，让 Agent 快速回忆"上周讨论的那个方案"。大多数 Agent 没这个能力。
- **moa（Multi-model Orchestrated Answering）**：同时调用多个 LLM，综合多个模型回答。适合事实核查、技术判断。
- **cronjob**：**用自然语言定义定时任务**。说"每天早上 9 点帮我看 GitHub"就行，不用写 cron 表达式。

#### Toolset：按需启用，不是全开

全开 40+ 工具不合理——管日程的不需要 code_execution，写代码的不需要 Home Assistant。

```yaml
# config.yaml 示例
toolsets:
  - web
  - terminal
  - file
  - skills
  - delegation
  # - homeassistant  # 不需要就注释掉
```

**Toolset 不只是功能开关**，还是：

- **效率工具**：启用越少，Agent 注意力越集中，token 消耗越少
- **安全边界**：Harness 的"约束层"在工具层面的具体实现

#### MCP:6000+ 应用的统一接口

40+ 内置工具是通用能力，但每个人工具栈不同——你可能用 Jira、Notion、Slack。**MCP 解决这个问题**。

```yaml
# 接入 GitHub MCP
mcp_servers:
  - name: github
    transport: stdio
    command: npx @modelcontextprotocol/server-github
    env:
      GITHUB_TOKEN: ${GITHUB_TOKEN}
```

配好后 Hermes 就能创建 Issue、审查 PR、查仓库状态。**即插即用**。

支持 **per-server 工具过滤**——MCP Server 暴露 20 个工具，你只想让 Agent 用其中 3 个，可以精确控制。

#### 子 Agent 委派(delegation)

Hermes 最强大的协调工具：

- **独立上下文**：每个子 Agent 有自己的对话历史，互不干扰
- **受限工具集**：调研子 Agent 只给 web+browser，编码子 Agent 只给 terminal+file
- **最多 3 个并发**：刻意的限制——超过 3 个，主 Agent 汇总质量急剧下降

> 与 Claude Code 多实例并行的区别：Claude Code 多实例是你手动开，实例间无协调。Hermes 子 Agent 是**Agent 自主决定何时分发、怎么汇总**。

#### 三重约束的安全模型

Agent 越强，约束越重要。Hermes 在工具层做了三重约束：

1. **Toolset 控制**：最粗粒度开关，只有启用的工具才能调用
2. **code_execution 沙箱**：代码在隔离环境运行，不影响宿主文件系统
3. **子 Agent 受限工具集**：调研 Agent 不需要也不应该有 terminal 权限

> **生产环境建议**：只启用必要 Toolset，通过 MCP per-server 过滤进一步限制。**宁可 Agent 来问"我需要 XX 权限"，也不要默认全开**。

## 五、作者推荐的四大实战场景

### 🎯 场景一：个人知识助手（§12）

**典型用例**：持续三周的领域调研项目（如调研 AI Agent 部署方案）

**Hermes 的破局点**：

- 传统 AI 每次开新对话都要花 3-5 分钟重新铺垫背景
- Hermes 的三层记忆让你**只说「继续」就能继续**
- 持久记忆存摘要（几百字），需要细节时用 FTS5 检索原始对话
- Honcho 用户建模会推导你没说的偏好（如"对成本敏感"）

**作者亲身体验**：用了两周后，Hermes 开始自动用短句回复，因为它发现作者倾向于直接要结论。

**适用判断**：任务越长、上下文越复杂，记忆带来的效率增益越大。一次性任务用不上。

---

### 🛠 场景二：开发自动化（§13）

**典型用例**：7×24 小时的代码巡检管家

**核心能力组合**：

| 功能 | 实现方式 |
|---|---|
| 自动代码审查 | GitHub MCP + 审查标准 Skill（规则会自动演进） |
| 测试生成与执行 | file + code_execution + terminal 组合 |
| 日报/周报汇总 | GitHub MCP + 跨会话记忆，理出因果关系 |

**作者画的早晨画面**：打开电脑，Telegram 弹出三条 Hermes 消息——昨晚 PR 的审查报告、凌晨 CI 测试结果、今日日报初稿。

**与 Claude Code 的分工**：

- **Claude Code = 工匠**（写代码、重构、调试）
- **Hermes = 管家**（巡检、监控、汇总、调度）

> ⚠️ **提醒**：Hermes 的代码审查是辅助而非替代，核心模块仍要保留人工 review。

---

### ✍️ 场景三：内容创作（§14）

**典型用例**：连续写一个五篇的系列选题

**Hermes 解决了一个老问题**：

> Claude Code 每次开新会话都不记得上一篇文章的教训。这周说别用"综上所述"，下周又冒出来。

**三大创作加速器**：

1. **持续性记忆**——第二篇开始，直接说"写系列第二篇"，不用重新讲风格、读者画像、已写过的话题。

2. **子 Agent 并行调研**——写竞品对比时，同时派出三个子 Agent：
   - 子 Agent 1 调研 Hermes 架构
   - 子 Agent 2 调研 OpenClaw 生态
   - 子 Agent 3 搜集社区反馈
   
   原来 1 小时的调研，20 分钟搞定。

3. **写作风格 Skill 自动积累**——你审校时做的修改，Hermes 会观察并学习。连续三次把"进行优化"改成"优化一下"，它就在 Skill 里加一条"避免'进行+动词'句式"。一个月后变成你的**专属编辑手册**。

**作者的真实工作流**：

- 单篇商单文章 → Claude Code（交互快、可即时调整）
- 系列选题和个人专栏 → Hermes（让写作 Skill 慢慢长出来）

---

### 🐎 场景四：多 Agent 编排（§15）

**典型用例**：复杂任务的并行加速

**delegate_task 的关键设计**：

| 特性 | 说明 |
|---|---|
| 独立上下文 | 子 Agent 不污染主 Agent |
| 受限工具集 | 调研 Agent 只给 web+browser，编码 Agent 只给 terminal+file |
| 并发上限 3 个 | 超过 3 个，主 Agent 的汇总质量会急剧下降 |

**实战案例**：竞品分析报告（对比 Claude Code、Cursor、Hermes）

1. 主 Agent 定义任务模板（定位、功能、架构、定价、社区、优缺点）
2. 派出三个子 Agent 并行调研
3. 主 Agent 汇总成对比报告

**总时间**：从 `A+B+C` 变成 `max(A, B, C)`

**受限工具集的双重价值**：

- 效率：工具越少，Agent 注意力越集中
- 安全:即使搜到恶意代码片段,没有 terminal 权限也无法执行

> ⚠️ **反模式**：不是所有任务都要拆子 Agent。如果你给主 Agent 写很长的汇总指令来整合结果，说明拆分有问题——好的拆分应让汇总变简单。

## 六、三个工具的定位对比

| 维度 | Claude Code | OpenClaw | Hermes Agent |
|---|---|---|---|
| 核心理念 | 交互式编码 | 配置即行为 | 自主后台+自改进 |
| 你的角色 | 坐在终端前指挥 | 写配置定义行为 | 部署后偶尔检查 |
| 运行模式 | 按需启动 | 按需启动 | 24/7 后台运行 |
| 比喻 | 工匠 | 标准化模板 | 管家 |

**作者结论**：不是选择题，而是组合题。

- 白天团队 → Claude Code（需要你在场的事）
- 夜班团队 → Hermes（不需要你在场的事）

## 七、深度思考：自改进 Agent 的边界

### 核心矛盾

> **自主 Agent 的价值在于你不用盯着，但安全需要你盯着。**

### 技术上受控的三道防线

1. Skill 是可读的 markdown（非黑箱权重）
2. 记忆数据本地化（SQLite 可直接查看）
3. 工具权限有沙箱（需显式配置）

### 自改进的天花板

**不在技术，在反馈信号**。Agent 不知道自己不知道什么，只能在「已知方向」上越跑越快，**方向本身仍需人来定**。

### 留给读者的几个问题

- 你愿意让 Agent 自主改进到什么程度？
- 谁来审计自改进的结果？
- Agent 需要「遗忘」机制吗？
- 如果 Agent 自己设计自己的缰绳，谁来判断缰绳设计得对不对？

> 「Hermes 是第一个出厂就带缰绳的 Agent。而且缰绳会自己长大。」

> 「OpenClaw 是你养出来的龙虾，Hermes 是自己会长大的龙虾。」
